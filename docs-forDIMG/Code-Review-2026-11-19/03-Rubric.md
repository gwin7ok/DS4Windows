## 1. 目的と使い方

報告書 §1.2 の A〜D は、私の判断で付けた目安だった。数字（`Measure-CodeReview.py`）は毎回同じ方法で取り直せるが、A〜D は評価する日で基準が動く。そこで、**どの数字がいくつなら何点、何点なら何等級**を先に固定し、各 PhaseRV の最終 Step で同じ手順で採点する。

```bash
python -I scripts/audit/Score-CodeReview.py                      # 採点して表示
python -I scripts/audit/Score-CodeReview.py --calibration        # 2026-11-19 の評価を再現できるか確かめる
python -I scripts/audit/Score-CodeReview.py --json docs-forDIMG/Code-Review-2026-11-19/scorecard/RV1.json --label "RV1 完了" --diff docs-forDIMG/Code-Review-2026-11-19/scorecard/RV0-baseline.json
python -I scripts/audit/Score-CodeReview.py --forecast           # 机上の予想
python -I scripts/audit/Score-CodeReview.py --show-rubric        # §3 の表（スクリプトの値が正）
```

ソースは変更しない（読むだけ）。所要は約 10 秒。

## 2. 点数の出し方

1. **指標**: 観点ごとに 4〜8 個。数値の指標（`Measure-CodeReview.py` や基準ファイルから自動で取る）、手で記録する数値（`Rubric-Inputs.json` の `manual`）、はい／いいえの確認項目（同 `checklist`）の 3 種類。
2. **指標の点（0〜1）**: 数値は、**目標値で 1、下限値で 0、その間は直線**。確認項目は、はいで 1、いいえで 0。
3. **観点の点数**: 指標の点を**重みで平均**する（重みは §3 の表）。
4. **等級**: 固定の等級表で A〜D に直す。

| 点数 | 等級 |
|---|---|
| 90% 以上 | A |
| 83% 以上 | A− |
| 76% 以上 | B+ |
| 69% 以上 | B |
| 62% 以上 | B− |
| 55% 以上 | C+ |
| 48% 以上 | C |
| 41% 以上 | C− |
| 41% 未満 | D |

等級の意味は報告書と同じ。**A**＝目的をほぼ満たし、残りは細部。**B**＝骨格は良く、名指しできる欠けがある。**C**＝主な目的が満たされていない。**D**＝方針そのものがない。

**目標値と下限値の決め方**: 目標値は「指摘する人がいなくなる水準」。計画書に完了の定義の値があるものは、その値。下限値は「方針がない状態」の目安。どちらも丸い数字（10、20、50、100、200…）から選び、細かい調整はしていない。

| 機能追加の容易化 | B | B | 71.5% | 2.5 点 |

**注意（正直に書く）**:
- 目標値・下限値・重みは、**この一致を見ながら決めた**（スクリプトに入れる前の紙の上の試算では、冗長処理が C−、メンテナンス性が D 台になったため、重みと下限値を直してから入れた）。つまり、**現状の等級が正しいかを、この基準で検証したのではない**。現状の等級は、報告書の判断を出発点（基準点）として置いた。
- 検証できるのは、**改善で数字が動いたときの、向きと大きさ**（どの指標がいくつ動いて、観点の点数が何点動いたか）。等級の絶対値より、**点数（%）と前回との差**を見ること。
- 太字の 4 観点は、下の境界まで 1〜2 点。数字が少し動くだけで等級が 1 段変わるので、**等級が下がっても、点数が上がっていれば改善**と読む（`--diff` が点数の差を出す）。
- 文書の数（`mt_docs`）は、この計画を書いたこと自体で増えた（474 → 482）。基準点は、文書を足し終えたあとの状態で保存する（`scorecard/RV0-baseline.json`）。

### 以前の目分量の予想との違い

報告書の追加説明で、私は最終を「A−（MVVM とオブジェクト指向は B+）」と予想した。この基準で計算すると、**目標どおりに進めば、いくつかの観点がそれより高く出る**。

- **各層の役割分担・MVVM・共有部品化・機能追加の容易化・冗長処理・採用手段の統一が A**: 基準の目標値が、計画書の完了の定義の値と同じなので、達成すれば指標が満点近くになる。目分量のときに差し引いた「許可リストに残る見た目だけの処理」「`BackingStore` の袋」は、MVVM では指標の点（結びつけ率、ViewModel の割合）に出るが、**重みが小さい**ので全体を下げきらない。
- **オブジェクト指向は B**（目分量の B+ より低い）: `BackingStore` の公開フィールド 107 と、500 行以上のファイル 32 が、どの Phase でも動かないため。
- **A は「基準の指標が目標値に届いた」という意味**で、「完璧」ではない。基準に入れていないもの（§8）は、評価に出ない。

この差は、基準が悪いからではなく、**目分量が、数字にしていない懸念を含めていた**から。数字にしていない懸念は、§8 に列挙し、必要なら指標を足す（版を上げる。§6）。

## 6. 基準を動かさない規則

- 目標値・下限値・重み・等級表（`Score-CodeReview.py` の `VIEWPOINTS`・`BANDS`）は、**承認のあと、Phase の途中で動かさない**。都合のよい動かし方（点が足りないから下限値を下げる、など）を防ぐため。
- 直したいときは、**基準の版（`RUBRIC_VERSION`）を上げ、ユーザーの承認を得て**、過去の保存（`scorecard/*.json`）をすべて新しい版で採点し直してから比べる。版が違う保存どうしは、`--diff` が警告を出す。
- 新しい指標を足す（PhaseRV9 などの計画書で、検出の方法が決まったとき）のも、版を上げる扱い。
- **確認項目の答え**（`Rubric-Inputs.json` の `checklist`）は、Phase の最終 Step で、根拠を確かめてから更新する。「はい」にするときは、実行したテストの名前・コマンド・日付を `evidence` に書く（例: `DeviceLoopStructureTests` が Debug ALL で通る）。根拠を書けないものは「はい」にしない。
- **手で記録する値**（`manual`）も同じ。`profile_setting_files` は、RV5-1 で、設定の項目を 1 つ足す手順を実際にたどって数え直す。`nullable_layers_enabled` は、PhaseRV9 の計画書で、層ごとの有効化の検出方法を決める（それまでは手で書く）。
- スクリプトが、`Measure-CodeReview.py` の出力の書式から数字を読めないときは、**止まって知らせる**（0 として黙って進めない）。

## 7. 各 Phase の最終 Step「評価の再算定」

各 PhaseRV の計画書の最後に、次の Step を足した（`RVn-最後`）。

1. `python -I scripts/audit/Score-CodeReview.py --json docs-forDIMG/Code-Review-2026-11-19/scorecard/RVn.json --label "RVn 完了" --diff <直前の保存>` で、採点して保存する。
2. `Rubric-Inputs.json` の確認項目と手入力の値を、根拠（実行したテスト・実測）を `evidence` に書いて更新してから採点する。
3. `02-Scorecard.md` に、その Phase の列を足す。**等級が変わった観点**と、**点数が動いた指標とその理由**（`--diff` の表を元に）を書く。予想（§5）とずれたら、その理由を書く。
4. `01-Metrics.md` §13 の「現在」の列を、`Measure-CodeReview.py` の実測で取り直す。
5. ユーザーへ、点数と等級の変化、予想とのずれ、次の Phase で動かす指標を報告する。

この Step は、ソースを変更しない（記録だけ）。コミットは文書とスコアカードのみ。

## 8. この基準が測っていないもの

次は、基準に入っていないので、**等級が上がっても保証されない**。別の確認（実機確認、レビュー）で見る。

- 実機での動作（機器の抜き差し、切替、ホットキーなど）。Phase ごとの実機確認で見る。
- テストの質（件数・割合は見るが、検査の強さは見ない）。RV8-5 の分類表で見る。
- コメント・文書の読みやすさ（`Phase<数字>` の行数は数えるが、文の質は見ない）。
- 命名の意味、責務の切り方の良し悪し（大きなファイルの数は数えるが、分割の正しさは見ない）。
- 計測の誤差: 構造の重複・未参照・インターフェースの数え方は、正規表現による近似で、数件〜数%の誤差がある。同じスクリプトの前後で比べる。
- 未参照の型（`unref`）は、誤検出が多く（入れ子の型、拡張クラス、XAML の拡張）採点には入れていない。
