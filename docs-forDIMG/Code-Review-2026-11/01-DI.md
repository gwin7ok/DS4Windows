# コードレビュー（2026-11）観点 1: Pure DI の強みを生かせる構成

作成日: 2026-11-11（対象のコミットと読み方は `00-Summary.md`）

## 1. 良い点（維持すべき設計）

- `AppHost` を使うのは `App` と `Composition` だけ。`IServiceProvider` を持つのは `MainWindowFactory` だけで、理由（窓の依存の一覧を二重に持たない）がコメントにある（`DS4Windows/Composition/MainWindowFactory.cs:21`）。
- `Func<T>` の遅延解決は 2 件だけで、どちらも循環の理由が書かれている（`DS4Windows/Composition/ServiceRegistration.Processing.cs:105` の `Func<IActionBindingBuilder>`、同 160 行の `Func<IMapping>`）。
- 後付けの配線は 3 件に絞られ、1 つのメソッドに集まっている（`DS4Windows/Composition/ServiceRegistration.Wiring.cs:26`）。3 件とも原因は同じで、`BackingStore` をコンテナより前に作ること。コンストラクターで渡せるものは残っていない。
- 時計は `TimeProvider` を注入しており、マクロの待ち・キーのリピート・ライトバーをテストで差し替えられる（`ServiceRegistration.Core.cs:26`）。
- 機種の登録は `AddInputDevice<TCartridge, TModule>()` の 1 行、出力の種類は `IOutputDeviceCartridge` の列で、同じ契約の依存を列で受ける形になっている。
- 状態を持つ Singleton（`SyntheticInputState`、`MacroRuntimeState`、`StickMotionState`）と、状態を持たない処理の段が分かれている。

## 2. 問題点

### 1-1（中）配列の中身を、別の型のコンストラクターが作る
- 場所: `DS4Windows/Processing/Services/InputReportProcessor.cs:92`〜`97`、`DS4Windows/Processing/Services/DeviceSlotState.cs:13`、`18`
- 事実: `DeviceSlotState.CurrentStates` は配列だけを作り、要素（`ControllerState`）は `InputReportProcessor` のコンストラクターが作る。`DeviceSlotState` のコメントにも「`CurrentStates` は `InputReportProcessor` が作る」とある。
- なぜ問題か: `InputReportProcessor` が解決されるより前に `CurrentStates[i]` を読むと `null` になる。生成の順序への依存が、型にも登録にも表れていない。テストで `DeviceSlotState` だけを作ると、本番と違う状態になる。
- 修正の方向: `DeviceSlotState` が自分のコンストラクターで作る（`PreviousStates`・`TempStates` はすでにそうしている）。`ControllerStateExposed` の配列も、持ち主を 1 つにする。

### 1-2（中）破棄の順序が、型で表れていない
- 場所: `DS4Windows/App.xaml.cs:920`〜`975`（`CleanShutdown`）、`DS4Windows/Processing/Services/RuntimeBootstrapper.cs:79`、`DS4Windows/Composition/AppHost.cs:188`
- 事実: 登録されたサービスのうち `IDisposable` を実装するのは `IpcMemoryMap`、`LowLevelMouseHook` など少数で、出力・デバイス・イベントスレッドのサービスは実装していない。そのため `AppHost.Dispose()` は実質何も破棄しない。破棄の順序（サービスの停止 → `RuntimeBootstrapper.Shutdown` → 設定の保存 → タイマーの解像度 → 単一起動 → IPC → ボタンのコントローラーの破棄 → ホストの破棄 → ログ）は、`CleanShutdown` の手書きの並びだけが守っている。
- なぜ問題か: ドライバーの破棄順序はガードレール（`Phase5-Plan.md` §5）なのに、守っているのが `App` の 1 メソッドの行の並びである。部品を足したとき、どこへ入れるかの手がかりがない。
- 修正の方向: 終了の手順を 1 つの型へ集め、`App` は呼ぶだけにする。順序は、ソースの並びではなく、呼び出しの記録で確かめるテストで固定する。

### 1-3（中）`App` が約 15 個のサービスを個別に解決して持つ
- 場所: `DS4Windows/App.xaml.cs:70`〜`88`（フィールド）、`652`〜`672`（`InitializePostHostServices`）、`678`（`ResolvePostHostService`）
- 事実: `App` は `AppHost.GetService` で 15 個前後のサービスを解決し、フィールドに持つ。規則（`AppHost` を使えるのは `App` と `Composition`）の範囲内ではある。
- なぜ問題か: `App` が、設定の保存・ボタンのコントローラーの後始末・HidHide の確認などの業務を直接握る原因になっている。`App.xaml.cs` は 978 行ある。
- 修正の方向: 起動後の処理と終了の処理を `Composition/Startup` の部品へ出し、`App` が解決するのは 1〜2 個にする。

### 1-4（低）登録の中で、具象へキャストしている
- 場所: `DS4Windows/Composition/ServiceRegistration.Processing.cs:175`（`(IConfigurableDeviceLookup)sp.GetRequiredService<IDeviceSlotState>()`）、`DS4Windows/Composition/ServiceRegistration.Wiring.cs:50`（`as ProfileSettingsService`）、`DS4Windows/Composition/AppHost.cs:129`（`as DefaultActionManager`）
- なぜ問題か: 偽物に差し替えると、キャストは例外になり、`as` は `null` になって配線が黙って抜ける。
- 修正の方向: 契約に必要なメンバーを足すか、具象を別のサービス型として登録する。

### 1-5（低）静的な差し替え口が残る
- 場所: `DS4Windows/Processing/Actions/RepeatHelperToIRepeaterAdapter.cs:21`（`RepeaterFactoryOverride`）
- 事実: `Phase7-Residual-Ledger.md` に持ち越しとして記載がある。
- 修正の方向: 工場をコンストラクターで受ける。

### 1-6（低）ロガーの静的イベントが業務の通知を運ぶ。静的な可変の設定がある
- 場所: `DS4Windows/Core/Logging/AppLogger.cs:27`、`29`（`GuiLog`、`ProfileChanged`）、`119`（`_notificationService`）、`DS4Windows/Core/Platform/KeyboardSettings.cs:11`〜`21`、`DS4Windows/App.xaml.cs:65`（`logHolder`）
- なぜ問題か: 「プロファイルが変わった」という業務の通知が、ロガーの静的イベントに載っている。テストで購読が残る。
- 修正の方向: 通知は DI のサービスへ、キーボードの設定は注入する値へ。ログの文言は変えない。

## 3. 寿命について

- Singleton／Transient の使い分けは、方針（`03-Lifecycle-and-DI.md` §2）どおりで、ずれは見つからなかった。Scoped は使っていない（スコープを作る場面がない）。
- `HttpClient` を Singleton で 1 つ持つのは適切（`ServiceRegistration.Core.cs:64`）。
