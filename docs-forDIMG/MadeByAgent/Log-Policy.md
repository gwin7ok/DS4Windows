# ログ出力の方針（Log-Policy）

作成日: 2026-11-03
状態: **承認済み（2026-11-03）。規約 §2.3 に反映済み**。決定の経緯は `Phase12-Step1-Plan.md` §6、現状の実測は `Phase12-Step1-Log-Inventory.md`。
適用: 新しいコードは、この方針に最初から従う。既存コードの一括整理は Phase13b（L2）で行う。**L2 までは、既存のログの文言・レベルを変えない**（規約 §2.3。改定案は §9）。

## 1. 基本原則（出し先とレベル）

- すべてのログに**レベル**を付ける（Trace／Debug／Info／Warn／Error）。出し先はレベルで決まり、API の名前で出し先を分けない。
- 画面（ログタブ）に出すかどうかは、レベルとは独立した**「利用者向け」の印**で決める（§3）。
- ログの入口は `AppLogger` に一本化する（§7）。

## 2. レベルの基準

| レベル | 基準 | 例 |
|---|---|---|
| Trace | 毎フレーム・高頻度の経路追跡 | 入力ループ、出力の送出 |
| Debug | 開発者向けの状態・分岐（低頻度） | 設定の読み込み結果、分岐の選択 |
| Info | 利用者にも意味のある出来事 | 接続・切断、プロファイル適用、起動・停止 |
| Warn | 異常だが継続できる | フォールバック、不正な入力 |
| Error | 処理の失敗 | 例外、機能不能 |

判定の問い（この順に聞く）: ①処理が失敗したか（Error）→ ②異常だが継続したか（Warn）→ ③利用者にも意味があるか（Info）→ ④1 秒に何度も出うるか（Trace）→ それ以外は Debug。

## 3. 画面（GUI）に出す基準

- 表示の候補は Info／Warn／Error のみ。Trace／Debug は表示できない。
- そのうち「利用者向け」の印があるものだけを表示する。一時表示（`temporary`）は印の変種で、ファイルには出さない。
- 利用者向けの文言はリソース化し、言語設定に従う（4.2.3 の前例）。

## 4. 接頭辞

- DI の境界を通過する重要操作には `[DI]` を付ける（規約 §2.3 を維持）。
- それ以外は `[機能名]` の形に揃える。
- 診断用の一時的な接頭辞（`[Diag-Toast]` など）は、恒久コードに残さない。

## 5. 文言の書式

- ファイルログ・診断ログは英語。
- 値は `key=value`。例外はメッセージ＋型名。
- 利用者向けの文言は §3 のとおりリソース化する。

## 6. 高頻度経路のガード

- Trace／Debug で、補間文字列・連結・割り当てを伴うログは、`IsTraceEnabled`／`IsDebugEnabled` のガードを必須とする。定数文字列のみなら不要。
- 入力ループ（毎フレーム）は常にガードする。

## 7. 出力経路

- `Console.WriteLine`／`Debug.WriteLine` は使わない（AppLogger を使う）。
- NLog の直接呼び出しは、ログ基盤（`LoggerHolder` など）の内部に限る。
- API は汎用の `Log(level, message, options)` に集約する（`options` に利用者向けの印・一時表示）。各サービスの private `LogDebug` と `AppLogger.TrayIconLog` は廃止する。`LogToTray`（通知）の位置づけは L2 の計画書で詰める。

## 8. テストでの扱い

- ログを期待値にするテストは、文言の完全一致ではなく、レベルと主要語（`key=value` など）で検査する。

## 9. 規約 §2.3 の改定案（承認後に反映）

現行: 既存のログ出力とログレベルの完全な維持。案:

> - 通常の Phase では、従来どおり、既存のログの文言とレベルを維持する。
> - ログ整理の Phase（13b）に限り、`Log-Policy.md` に沿った変更を許可する。変更は「レベルのみ／文言／削除」に分けて記録し、利用者に見える GUI・トレイのログの変更は一覧で承認を得る（Phase8-Step8-Q7 の前例）。
> - 新規のコードは、最初から `Log-Policy.md` に沿って書く。
> - DI の境界を通過する重要操作に `[DI]` を付ける規約は維持する。

## 10. L2（Phase13b）への申し送り

- 対象は 666 か所・101 ファイル（`Phase12-Step1-Log-Inventory.md`）。API の集約（§7）は変更量が最大のため、旧 API を薄いシムとして残す期間を設けて段階的に移行する（規約 §2.1）。1e で作業量を再見積りする。
- 旧 API の GUI・トレイの挙動（`warning` の真偽による Info／Warn の振り分け、`temporary`）は、新 API で同じ出力になるよう対応表を作る。
