# Phase17-5 計画書: 既存の入力機種を共通のデバイスへ移す

作成日: 2026-11-10
前提: `Phase17-Plan.md` の 17-5。当初は「移さない」と判断したが、2026-11-10 にユーザーが「実機のない 4 機種も DS4 と同じ状態まで移したい。実機確認は全て終わった段階で、実機を持つ人に依頼する」と決めたため、Phase17 の中で行う。

## 1. 目的と終わりの状態

- `DS3Device`・`DualSenseDevice`・`SwitchProDevice`・`JoyConDevice`・`DS4Device` の読み取りループ（各 300〜1,500 行）を、共通のデバイス（`ProtocolDevice`）と、機種ごとのプロトコル＋部品の組み合わせへ置き換える。
- 終わりの状態: 機種ごとのファイルは「プロトコル（バイト列との変換）」と「その機種だけの部品」になり、読み取りのループ、時間の管理、遅延計測、アイドル切断、出力の書き込みの時機は共通の 1 か所に集まる。`DS4Device` の継承による機種の派生を廃止する。
- 守るもの: 動作の完全維持（2.2）。ログの文言（2.3）。実機のない機種は、旧実装との差分テストで守る。

## 2. 現状の調査（2026-11-10）

| 機種 | ファイル | 行数 | 読み取りの方式 | 機種固有の主な動作 |
|---|---|---|---|---|

| DualSense | `Devices/DualSenseDevice.cs` | 1,466 | `ReadFile` | タッチパッド、ジャイロ、アダプティブトリガー、ミュート LED、BT の CRC |
| Switch Pro | `Devices/SwitchProDevice.cs` | 1,380 | `ReadFile` ＋ サブコマンドの送受信 | 初期化のやり取り、ジャイロの校正、レポートの種類の切り替え |

## 3. 方針: 守りを先に、共通化は段階的に

実機があるのは DS4 だけなので、次の順序を守る。**各段階の終わりで、全テストが合格し、DS4 の動作が変わらないこと**を条件にする。

| 段階 | 内容 | 守り |
|---|---|---|
| 17-5a | 旧実装の特性テスト（characterization）: `FakeHidTransport` に台本の入力を与え、旧機種ごとに「状態の列（`DS4State`）、出力レポート、`Removal` の順序、電池・充電の更新」を記録する。機種ごとに数十フレームの台本（ボタン・スティック・トリガー、電池の変化、切断）を用意し、期待値は旧実装の出力そのものとする | この記録が、以降のすべての移行の基準になる |
| 17-5b | `ProtocolDevice` を拡張する差し込み口を設計: 入力の取得方式（`ReadFile`／特徴レポートのポーリング）、時間の計算（機種のタイムスタンプ／システム時計）、動き（ジャイロ・加速度）の取り込み、タッチパッド、アイドル切断の規則、遅延計測 | 既存の `ProtocolDeviceTests`（偽の機種）が不変であること |
| 17-5c | DS3 を移す（最も単純。特徴レポートのポーリングとタイムスタンプ、ジャイロの取り込みが入る）。17-5a の記録と一致すること | 差分テスト |
| 17-5d | DualSense → Switch Pro → Joy-Con の順に移す（機種ごとに別コミット）。サブコマンドの送受信は、プロトコルの「初期化の手順」として切り出す | 各機種の差分テスト |
| 17-5e | DS4 を移し、`DS4Device` の継承による機種の派生を廃止する。DS4 は実機で確認できる | 差分テスト＋実機 |
| 17-5f | 文書（モデル図 01・02、規則）、検査（継承していないことを `LayerDependencyRuleTests` 等で）、基準値の更新 | |

## 4. リスクと見送りの条件

- 差分テストが確かめられるのは「台本に書いた入力」までで、実機特有のタイミング、再接続、BT と USB の切り替えは確かめられない。実機のある人が、移行後の各機種で確認する（`Known-Issues-Ledger.md` §3、完了報告書に確認項目の一覧を載せる）。
- ある機種で旧実装との差分が説明できないとき、その機種は旧実装のまま残し、理由を記録する（機種ごとに別コミットなので、残す・戻すが独立にできる）。
- 毎フレームの経路のため、割り当てを増やさない（既存の割り当て 0 のテストを維持）。

## 5. 進捗

- 2026-11-10: 計画書を作成。
- 2026-11-10 **機能廃止（ユーザーの承認）**: DS3 と Joy-Con は、現役で使われている可能性が低く、後継機が出ているため、機能ごと廃止した（コードの削除）。DS3 専用だった「ジャイロ擬似（UseDs3PitchRollSim）」の設定・画面・DS4 への出力補正・サービス再起動の要求・Joy-Con の結合（`JoyConLinker`）・Joy-Con／DS3 の設定の入れ物・解析器・テストも合わせて削除した。保存済みの設定ファイルにある該当の節・要素は、読み込みで無視される（書き出さない）。`InputDeviceType` は 3 値（DS4、SwitchPro、DualSense）になった。移行の対象は DualSense・Switch Pro・DS4 の 3 機種になる。テストは 3,366 件合格。
- 2026-11-10 **17-5a 完了**: DualSense・Switch Pro・DS4（いずれも USB）の特性化テストを追加した（`DualSenseDeviceBehaviorTests`、`SwitchProDeviceBehaviorTests`、`Ds4DeviceBehaviorTests`）。台本の入力に対する状態の列・電池・出力レポート・台本が尽きたあとの切断を、旧実装の記録として固定した。Switch Pro は初期化のサブコマンドの応答と校正値も台本にした。`FakeHidTransport` に読み取りの遅延（`ReadDelayMs`）を足した（Switch Pro は 5ms 未満の間隔のフレームを読み飛ばすため）。
- 2026-11-10 **17-5b の第 1 段（共通部品の集約）完了**: 3 機種のループに同じ形で複製されていた「遅延の窓」（`LatencyWindow`）、「アイドル切断の規則」（`DS4Device.EvaluateIdleDisconnect`）、「積まれた処理の実行」（`DS4Device.RunQueuedInputEvents`）を共通部品に集約した。3 機種の特性化テストは変わらず合格（全 3,371 件合格）。
- **残り（次の段）**: 時間の計算（機種のタイムスタンプ）、タッチパッド・動きの取り込み、入力の検証（BT の CRC・レポート ID）を `ProtocolDevice` の差し込み口にし、DualSense → Switch Pro → DS4 の順に移す。`DS4Device` は UI・割り当て・出力側が型として広く参照している基底であり、継承の廃止は影響が大きい。各機種で旧実装との差分が説明できない場合は旧実装を残す（4 章）。
- 2026-11-10 **17-5b の第 2 段**: タイムスタンプからの経過時間の計算を `TimestampClock` に集約（DS4 は 16 ビットで 16/3、DualSense は 32 ビットで 1/3）。`ProtocolDevice` も `LatencyWindow` と `RunQueuedInputEvents` を使うようにした（これまで遅延を計っていなかった）。テスト 3,374 件合格。
- **残り**: タッチパッド・動きの取り込みと入力の検証（BT の CRC・レポート ID）の共通化、出力レポートの組み立て（DualSense は約 300 行）のプロトコルへの移動、機種のデバイス固有の動作（トリガー効果、ミュート LED、校正の読み出し、Switch Pro の初期化）の置き場所の決定。その後、機種ごとに `ProtocolDevice` へ移す。
