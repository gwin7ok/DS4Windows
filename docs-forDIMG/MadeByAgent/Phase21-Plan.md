# Phase21 計画書: 同じ契約の依存を「列」で受ける（引数が多くなる根本原因の除去 その 3）

作成日: 2026-11-10
前提: 「引数 6 以上のコンストラクターを避ける根本的な対策」の検討の 3 番目（対策 3）。Phase19（工場の廃止）、Phase20（責務の分割）のあとに行う。
規則: 3.1（「何でも箱」を作らない。実行時に解決する Service Locator を使わない）、2.2、`IInputDeviceModule` の前例（同じ契約の複数の実装を、解決すると登録順の列で受ける）。

## 1. 目的と終わりの状態

- 「同じ契約を持つ依存を、1 つずつ別の引数で受けている」コンストラクターを、`IEnumerable<T>`（または `IReadOnlyList<T>`）1 つで受ける形に直す。機種・出力の種類・設定の領域など、種類が増えるたびに引数が増える形を無くす。
- 新しい種類を足すときに、受け取る側のコンストラクターを変えなくてよくする（拡張に開く）。
- 動作・ログは変えない。列の順序に意味があるものは、順序を保つ（登録順を固定し、テストで検査する）。

## 2. 前提と注意

- 対象の見つけ方は、型を見るだけでは分からない。「同じ契約 `I…`」か「役割の違う別々の契約」かの判断が要る。多くのコンストラクターの引数は、契約が違う（例: `IProfileSettingsService` と `IAppSettingsService` は別の窓口）。契約が違うものを無理に束ねると「何でも箱」になる。
- したがって、この Phase の最初の仕事は調査（Step 21-0）で、候補が少なければ、小さな Phase で終わる。候補が無ければ、その旨を記録して Phase を閉じる。

## 3. 設計の決定

| 番号 | 項目 | 決定 | 理由 |
|---|---|---|---|
| 1 | 対象の条件 | (a) 引数の型が同じ契約に属する、(b) 受け取り側が、それぞれを同じ手順で扱う（ループで足りる）、(c) 種類の追加で引数が増えうる。3 つとも満たすものだけ | 束ねるだけで依存が見えなくなる変更を避ける |
| 2 | 受け取る形 | `IEnumerable<T>` を受け、コンストラクターで `ToArray()` にして保持。登録順に意味があるものは、`ServiceRegistration` の登録順を固定し、並びのテストを足す | `IInputDeviceModule` の前例 |
| 3 | 識別が要る場合 | 種類で引き当てる必要があるなら、列に `Kind`（キー）を持たせ、受け取り側で辞書にする。名前の文字列での解決（キー付きサービス）は使わない | 型の安全を保つ |
| 4 | 対象外 | 契約が違う引数、実行時に判断して 1 つを選ぶもの（それは工場。Phase19） | 束ねる意味がない |

## 4. 段階

| 段階 | 内容 | 守り |
|---|---|---|
| 21-0 | 調査: 引数 6 以上の全型を反射で列挙し、同じ契約の引数が 2 つ以上あるものを抽出する。出力側の機種ごとの部品、設定の領域の窓口（`GyroSlotSettings` など）、入力機種のモジュールなど、候補を表にして、決定 1 の条件で選別する。候補が 0 件なら Phase を閉じる | 計画書の更新 |

| 21-2 | `ConstructorArityBaseline` と台帳・モデル図・ロードマップの更新 | `ConstructorArityRuleTests` |

## 5. リスク

- 列の順序が変わると、処理順（イベントの購読、初期化）が変わる。→ 決定 2 のとおり。
- 候補が少なく、効果が小さい可能性が高い。それでも調査の結果（「同じ契約の引数は無かった」）を記録する価値はある。

## 6. 進捗

- 2026-11-10: 計画書を作成。コードは未着手。
- 2026-11-10 21-0 調査の結果（Phase21 を閉じる）: 引数 3 個以上のコンストラクターについて、(a) 同じ型の引数が 2 つ以上あるもの、(b) 接尾辞が同じ契約の引数が 3 つ以上あるもの、をソースから抽出した。(a) は `TouchpadEventArgs`（`Touch` が 2 つ）、`TriggerBinding`（`SpecialAction` が 2 つ）、`ActionTypeDescriptor`（`ActionEditorModes` が 2 つ）で、いずれも値の入れ物で、数が固定の別々の役割。(b) は `CurveAndDeadzoneStage`（`IStickDeadZoneProcessor`／`IOutputCurveProcessor`／`ITriggerDeadZoneProcessor`／`IGyroControlsProcessor`）だけで、契約と呼び出しの署名が別々の段（同じ手順で扱えない）。決定 1 の 3 条件を満たす候補は **0 件**。よって **コードの変更なし**。種類の追加で増える複数の実装は、すでに `IInputDeviceModule` のように列で受けている（前例）。今後、同じ契約の実装を足すときの方針（列で受ける）は規則 3.1 に記載済み。Phase21 は調査のみで完了。
