## 目的
コードを読む人が、「今のコードの意図」だけを読めるようにする。経緯（どの Phase で何をしたか）は、git の履歴と `docs-forDIMG/` にあるので、コードのコメントからは外す。ただし、**設計の意図・理由・制約と、原則4 の TODO は、消さない**。あわせて、役目を終えたガードテストと、完了した Phase の文書を整理する。

## 方針・制約
- **コメントの整理は、コードの差分がないことを機械で確かめる**。各コミットで、コメントと空白を除いた構文が、前後で同じであることを検査する（`scripts/audit/Verify-CommentOnlyChange.py`、RV8-0 で作る）。
- 原則4 の TODO・設計意図・スレッド・循環・呼ばれる時点などの制約を述べるコメントは、残す。Phase 名・Step 名の参照だけを外すときは、その参照を除いても意味が通ること（その場合は、意味が通る形へ書き直す）。
- ログの文言（文字列）は、コメントではない。触らない。
- D1＝(B)（長すぎるコメントの要約）は、機械では「意味が同じ」を検証できない（検証できるのは、コードの差分がないことだけ）。そのため、(1) 要約の対象は、閾値を超えて意図が埋もれているものに限る、(2) 設計意図・原則4 の TODO・スレッド／循環／呼ばれる時点／順序の制約は、要約でも落とさない、(3) 要約したコメントは旧→新の対応表を層ごとに残し、ユーザーが抜き取りで確認する（各層 20 件程度。基準は RV8-0 で承認）。
- 文書は、削除ではなく `git mv` で `Archive/` へ移す（読むだけ。リンクの切れを検査）。規約・モデル図・台帳・未完了の計画書は、移さない。
- 規約本体（`.github/copilot-instructions.md`）の変更は、承認を得てから。

## リスク
- コメントの整理は低、**テストの全面的な見直し（D3＝(B)）と、コメントの要約（D1＝(B)）は中**。要約は意味の同一を機械で検証できず、テストの見直しは守りの喪失になりうる。対応表・抜き取りの確認・負の確認で抑える。
- 設計意図を含むコメントを、Phase 名の参照と一緒に削ってしまう危険がある。(c)(d) の分類を、候補の出力（スクリプト）→ 目で確認 → 置換、の順で行い、一括の自動置換はしない。
- ほかの Phase のブランチと衝突しやすい。この Phase を最後にする理由。
- 文書の移動で、規約・モデル図・コード内のコメントが指す文書のパスが切れる（コードのコメントが `docs-forDIMG/MadeByAgent/Phase…` を指す箇所がある。移動の前に、参照を検索して直す）。
