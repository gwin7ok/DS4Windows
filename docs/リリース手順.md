# リリース手順（バージョン管理・公開）

**基本は、VSCode の 2 つのキーで、リモートの公開（GitHub Release の作成）まで行う。**

| キー | タスク | 内容 |
|---|---|---|
| `ctrl+shift+2` | **Update Changelog** | 更新履歴の更新と、版の更新（`scripts/release-bump.ps1`） |
| `ctrl+shift+3` | **release-tag-and-push-short** | コミット → push → タグ → Actions がビルドと Release を作成（`scripts/release-tag.ps1`） |

> `.vscode/keybindings.json` は、割り当ての見本です。VSCode は、ユーザーの `keybindings.json`（コマンドパレット: 「Preferences: Open Keyboard Shortcuts (JSON)」）を読むので、そこへ同じ 2 つを写してください。

仕組みは、`Genshin-Rotation-Planner` のリリース手順と同じ流れを、このプロジェクト（.NET + PowerShell）に合わせたもの。

## 版の決め方
- **セマンティックバージョニング**（`主.副.修正`）。出どころは `Directory.Build.props` の `Version`（`FileVersion`・`AssemblyVersion` も同時に更新される）。
  - 主: 保存データ（プロファイル・Actions.xml）の互換を壊す変更、大きな作り直し。
  - 副: 機能の追加（互換あり）。
  - 修正: 不具合の修正・表示の変更・文書。
- タグは `v<版>`（例: `v4.0.1`）。`vX.Y.Z` の形だけが、リリースの対象になる。
- アプリの更新チェックは、GitHub の最新リリースのタグ（`v` を除いた版）と、実行ファイルの版を比べる。**タグと `Directory.Build.props` の版がずれると、更新の通知が繰り返される**ので、Actions が一致を検証する。

## 変更履歴（`CHANGELOG.md`）
- 英語。`## [x.y.z] - 日付` の節ごとに書く。**その版の節が、そのまま GitHub Release の本文になる**（アプリの更新画面にも表示される）ので、利用者に分かる文で書く。
- 手で `## [Unreleased]` に書いてもよい。空のままなら、Update Changelog が、前のリリース（最新のタグ `v*`）以降のコミットから生成する。
  - 載せる種類: `feat` → Added、`fix` → Fixed、`refactor`・`perf`・種類なし → Changed。載せない種類: `docs`・`test`・`chore`・`ci`・`style`・`build`・`diag`・`Release v…`・`Merge …`。
  - コミットの 1 行目が、そのまま文になる（末尾の「＊ビルド…」は外す）。**利用者に分かる文に、後で直す**。

## 通常のリリースの流れ
1. 変更を、ブランチで行い、リリースのブランチ（リモートの既定のブランチ。通常は `master`）にマージする。
2. そのブランチで、**`ctrl+shift+2`（Update Changelog）**:
   1. `[Unreleased]` が空なら、コミットから生成した内容を確認する（`Enter` = 書き込んで続行 / `e` = 書き込んで編集 / `n` = 中止）。
   2. 次の版を選ぶ（1 = パッチ / 2 = マイナー / 3 = メジャー / `x.y.z` を直接入力）。
   3. `Directory.Build.props` の版を更新し、`CHANGELOG.md` の `[Unreleased]` を `[x.y.z] - 日付` に切り出す。
3. `CHANGELOG.md` の文を確認・編集する（コミットはまだしなくてよい）。
4. ビルドとテストを、ローカルで確認する（Actions は、テストを実行しない）。
5. **`ctrl+shift+3`（release-tag-and-push-short）**:
   1. 前提の確認: 版の節が `CHANGELOG.md` にある・タグが未作成（ローカル・リモート）・リリースのブランチにいる・`origin` より遅れていない・`Directory.Build.props` と `CHANGELOG.md` 以外に未コミットの変更がない。
   2. 確認（`Enter` = 実行 / `n` = 中止）→ `Release vX.Y.Z` をコミット → ブランチを push → 注釈付きタグ → タグを push。
6. **以降は、Actions が自動で行う**（`.github/workflows/release.yml`。数分）:
   1. タグの形（`vX.Y.Z`）と、`Directory.Build.props` の版との一致の検証。
   2. タグのコミットが、既定のブランチに含まれることの検証。
   3. `CHANGELOG.md` から、その版の節を抽出（節が無い・空ならここで失敗）。
   4. x64 のビルド → zip の作成（`DS4Windows_<版>_x64.zip`）。
   5. 同じタグの Release があれば削除し、GitHub Release を作成して zip を添付。
7. Releases のページで、本文と zip を確認する。

事前の確認だけをしたいときは、タスク `release-tag: dry run`・`Update Changelog: dry run`（何も実行・変更しない）。

## 版の節がすでにあるとき（4.0.0 の最初のリリースなど）
`CHANGELOG.md` に `[x.y.z]` の節があり、タグが未作成のときは、`ctrl+shift+2` は不要（実行しても、「`ctrl+shift+3` でリリースできます」と案内される）。そのまま `ctrl+shift+3`。

## 失敗したとき
| 症状 | 対処 |
|---|---|
| `ctrl+shift+3` が、「タグがすでにある」と止まる | 版を上げる（`ctrl+shift+2`）。公開した版は付け直さない。ビルドの失敗など、公開前のやり直しだけ `release-tag.ps1 -Recreate`（既存のタグを削除して付け直す） |
| Actions が、「タグの版が Directory.Build.props と違う」で失敗 | タグを消し（`git tag -d` と `git push origin --delete`）、版を直してコミット・push してから、付け直す |
| Actions が、「タグのコミットが既定のブランチに含まれない」で失敗 | コミットを既定のブランチに push（マージ）してから、タグを付け直す |
| Actions が、「No changelog section found」で失敗 | `CHANGELOG.md` に、`## [x.y.z]` の節（本文あり）を書いてコミット・push し、タグを付け直す |
| `ctrl+shift+3` が、`master` ブランチではないと止まる | リモートの既定のブランチで行う。別のブランチで行うときは、`release-tag.ps1 -Branch <名前>` |

## 注意
- 版は、手で `Directory.Build.props` を書き換えず、Update Changelog で変える。
- リリースのリポジトリを移すとき（例: `gwin7ok/DS4Windows`）も、この手順は変わらない。更新チェックの参照先は `DS4Windows/Updater/ReleaseSource.cs` の `Repository`。
